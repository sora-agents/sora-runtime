# AGENTS.md

Guidance for coding agents working in this repository. Claude Code additionally reads [CLAUDE.md](CLAUDE.md), which imports this file and adds only the Claude-specific overrides.

## What this is

The S-ORA runtime — a runtime for practical agents in dynamic and asynchronous environments. The core runtime is implemented and tested in `src/sora/` — the decision cycle, activities, memory modules, action registry, and terminal CLI all exist and are covered by an extensive test suite (619 tests as of this writing). Check [ROADMAP.md](ROADMAP.md) before assuming something is or isn't implemented yet — it tracks only the work remaining before the first release, organized around release gates rather than build phases. The phase-structured record of what was *already* built, with its per-task "Done:" notes, is archived and frozen at [docs/development/roadmap-phases-0-4.md](docs/development/roadmap-phases-0-4.md). [README.md](README.md) remains the living spec, alongside [EXAMPLES.md](EXAMPLES.md) — but it is no longer the source of truth for types and signatures. Narrative documentation lives in [docs/](docs/), built as a MkDocs Material site (start at [docs/index.md](docs/index.md)); README.md is now a router into it. [docs/reference/python-api.md](docs/reference/python-api.md) is the *generated* type/signature reference (via `mkdocstrings`, rendered fresh on every `mkdocs build` directly from `src/sora/**/*.py`'s docstrings and type hints) — it is never hand-edited and never proposed as a diff. README used to carry its own hand-maintained API sketch; that's now archived verbatim (not maintained, can drift) at [docs/reference/api-sketch-notes.md](docs/reference/api-sketch-notes.md) for its narrative inline commentary, superseded by python-api.md as the authoritative contract.

## Commands

```
uv sync --all-extras --dev        # install pinned deps into .venv (uv provisions Python itself)
uv run ruff check .               # lint
uv run ruff format --check .      # format check (drop --check to auto-format)
uv run mypy                       # type check (strict)
uv run pytest                     # full test suite
uv run python3 scripts/check_manuals_sync.py  # EXAMPLES.md manuals == tests/fixtures/manuals/*.md
uv run pytest tests/test_smoke.py::test_package_importable  # single test
uv run pre-commit install         # one-time: run the same checks locally on commit
```

CI (`.github/workflows/ci.yml`) runs all five checks above (ruff lint, ruff format, mypy, pytest, manuals-sync) on Python 3.12 and 3.13 for every push/PR, plus a separate `docs` job that runs `mkdocs build --strict` once on Python 3.12 — `mkdocs.yml`'s `validation:` block turns a broken internal link, a bad `#anchor`, or a nav entry pointing at a missing file into a build failure there — treat a failure in any of them as a real failure, not noise. Run the full set locally before committing/pushing (or `uv run pre-commit run --all-files`). `check_manuals_sync.py` is the easiest to forget: it only runs on commit if `pre-commit install` has been done, so run it explicitly when you edit a manual in EXAMPLES.md / `tests/fixtures/manuals/` without a local pre-commit.

## Architecture

The design fixes a specific shape that the implementation follows — this is what would otherwise require reading all of README.md's API Sketch to piece together:

- **Decision cycle, not a single call.** An agent's core loop is five phases — Observe, Reflect, Situate, Reason, Act — executing at most one external action per cycle, even though many activities can be pursued concurrently. Each phase has its own independently pluggable strategy (`ObserveStrategy`, `ReflectStrategy`, `SituateStrategy`, `ReasonStrategy`, `ActStrategy`); pluggable never implies a model call, mechanical/deterministic defaults are first-class.
- **`TickResult` threads through all five phases.** It's the field-gating / short-circuit mechanism: each phase strategy receives and returns it, filling in whatever fields (`activity`, `step`, `invocation`) it can, and `DecisionCycle.tick()` only calls a phase's strategy if the relevant field is still `None` — a field an earlier phase filled short-circuits the later one. This is how "several focused calls" and "zero calls (cached plan, mechanical defaults)" are valid configurations of the same code, with no separate caching mechanism, and none should be added (see [ADR-0011](docs/architecture/adrs/0011-phase-fusion-via-threaded-result.md)). Model calls (infer/ground) run **off-cycle** as internal actions, not inside the phase, so "one fused Situate→Reason→Act call" is a narrow synchronous-mode option, not the goal — fusing selection into the model call re-serializes multi-activity concurrency (see [ADR-0021](docs/architecture/adrs/0021-llm-calls-as-async-internal-actions.md)).
- **Tools live behind adapters, grouped into Workspaces.** The runtime never authors tools ([ADR-0003](docs/architecture/adrs/0003-adapters-not-tool-authoring.md)); a `WorkspaceAdapter` imports them from an external ecosystem (MCP, WoT, ...) into the three-part usage interface (observable properties, signals, operations). A `Workspace` is the shared connection/lifecycle boundary; an individual `Tool` may still have its own address distinct from its workspace's ([ADR-0005](docs/architecture/adrs/0005-workspace-grouping.md)). A `Manual` describes a tool *type* and stays protocol-agnostic — protocol bindings (WoT forms/security, an MCP session) live on the live `Tool`, never in the manual; an adapter may synthesize a manual from a native description or pair the protocol binding with a hand-authored one, reconciled by type-level `Manual.id` ([ADR-0015](docs/architecture/adrs/0015-manuals-protocol-agnostic-adapter-boundary.md)).
- **`Agent` and `DecisionCycle` share constructed instances rather than one referencing the other.** Memory modules and communication are built once and hand the same objects to both; actions receive only `(tools, cycle)`, never a whole `Agent`. This is deliberate — see [ADR-0013](docs/architecture/adrs/0013-shared-instances-narrow-dependencies.md) before reintroducing a back-reference to fix a wiring inconvenience.
- **All wiring is centralized in `sora/bootstrap.py`.** A developer implementing an agent only ever writes `agent.yaml` plus, typically, one `ReasonStrategy` — never constructs `Agent`/`DecisionCycle`/memory modules by hand (see [docs/getting-started/configuration.md](docs/getting-started/configuration.md)).
- **Two independent kinds of waiting — don't conflate them.** Invoking any operation *unconditionally* moves the activity to `running` with `Activity.pending_operation` set; when the result resolves, the runtime transitions it back to `ready` automatically (unambiguous 1:1 match, no `Percept`, no strategy code). Firing an LLM call (infer/ground) via the `_infer_`/`_ground_` internal actions moves the activity to `running` the same way — with `Activity.pending_inference` (mutually exclusive with `pending_operation`) — and resolves 1:1 the same way, via `inference_sink` and still never a `Percept` (see [ADR-0021](docs/architecture/adrs/0021-llm-calls-as-async-internal-actions.md)); `running` thus has two resolve sources but remains one state, and inference-in-flight is a flavor of `running`, not a third kind of waiting. That resolve stays manual-agnostic — don't make `running`'s resolution manual-driven. A manual can *additionally* require waiting for a specific signal before the next step — that's `blocked`, **layered on top of** the resolve (a *separate* step, never fused into it), entered/exited via the `_suspend_`/`_resume_` internal actions and `Activity.blocked_on` (a `SignalWait`). It is **mechanical, not a judgment call**: the operation declares its completion signal in its manual (`OperationSpecification.completion_signal`, lifted from the authored `completes_on:` interface block), and `DefaultObserveStrategy` matches an observed signal against it by name equality — the suspend is done in **Observe** (after the resolve), not Reflect or Act (Act stays mechanistic per ADR-0017). An early completion signal (one that beats the ack) is recognized at suspend time so the two waits compose rather than deadlock — the signal itself is never destructively consumed at either suspend or resume, only the fixed retention cap ever evicts it, so the same signal instance can also satisfy another activity blocked on the same wait, or a strategy reading `WorkingMemory.signals` directly; a property-reaches-state completion is a foreseen second `blocked_on` form, deferred. Don't reintroduce an operation result as a `Percept` kind. See [ADR-0019](docs/architecture/adrs/0019-blocked-state-machinery-and-percept-storage.md).
- **Attention is reconciled in Observe, and focus is a subscription — not a view over memory.** Joining a workspace does *not* focus its tools. At the top of every Observe, before `_snapshot_properties`, a pluggable `FocusPolicy` recomputes the set of tools to attend to and the runtime focuses/unfocuses the difference. **Observe is the right home and this is the durable part**: `Tool.focus(sink)` wires the signal sink and establishes an adapter's change baseline, so it decides what can be perceived *at all* — deciding it in Situate's `_filter_` instead would put it structurally one tick behind the perception it gates. Reconciliation is a mechanical internal effect, never an external-action dispatch, so ADR-0009 holds. Focus gates three things, not one — property snapshotting, signal *production* at the adapter, and per-cycle diff work. The default is **`FocusAllJoined`** — reconciled every tick, but declining to narrow. `IntentionScopedFocus` is the **opt-in** narrowing policy, deriving the attended set from live intentions (steps' `tool_id`s except an `unfocus` step's, `$prop` tool ids found by walking params *recursively*, condition `watch` sources, `blocked_on` sources, in-flight operations) and broadening to every joined tool while an activity has no plan or the agent has none. Narrowing is opt-in because it measured at ~825 prompt tokens per model call and *zero* judge calls on both shipped configs, against a re-baselining risk that fails silently — not worth cents against a benchmark result. That policy choice is cheap to reverse, which is why it is a design note and deliberately not an ADR. It is selectable from `agent.yaml` as `strategies.focus` (`intention-scoped` / `all-joined` / a dotted path) — a sub-strategy of Observe, passed as a keyword, not a phase resolved on its own. Don't reintroduce auto-focus-on-join, and don't replace the recomputation with incremental leases: the union already *is* a refcount, and an incremental one goes silently blind on a double decrement. A second, **non-destructive** layer narrows the `PerceptSnapshot` at `_ground_`/`_select_` to the firing activity's own tools; planning, both judges and `_revalidate_` deliberately stay agent-level. That layer **follows the policy** via `WorkingMemory.attention_narrowed` (written from the policy's target, before `suppressed_tools` is subtracted) — keep it that way: an agent on the broad default declined to narrow *because* a wrongly narrowed view fails silently, so narrowing its prompts anyway reintroduces that risk one layer down. Two things the every-tick recomputation owes the rest of the runtime, both easy to drop by accident: an explicit `_unfocus_` is held in `WorkingMemory.suppressed_tools` and subtracted from the policy's target (otherwise the next tick recomputes the tool straight back and `_unfocus_` is a no-op), and a tick where the attended set actually moved re-anchors every activity's `reconsider_baseline` (otherwise the agent's own narrowing moves the ADR-0024 signature and buys a spurious `_revalidate_`). See [the design note](docs/architecture/notes/attention-scoped-to-live-intentions.md).
- **Properties and signals are stored separately in `WorkingMemory`, not one `perceptions` list.** `properties: dict[(source, name), Percept]` is a replace-by-key snapshot (persistent, re-observed state, last value wins); `signals: list[Percept]` is an append log — a matched signal is *not* evicted on `_suspend_`/`_resume_` (it stays available to any other waiter or direct reader); only a fixed retention cap bounds it, so an early or orphan signal survives to a later cycle the same way an unmatched one does. `Percept` has no `kind` field — the store discriminates. `_filter_`/`UnfocusAction` prune only `properties`; they never touch `signals`.
- **`signal_sink`/`result_sink`/`inference_sink` live on `DecisionCycle`, not `WorkingMemory`.** All three bridge asynchronous, off-cycle events into `tick()`, not settled state (`result_sink` carries invoke acks; `inference_sink` carries off-cycle infer/ground results — an `InferenceResult`, never a `Percept`). `signal_sink` specifically has to sit next to `interrupt()`, since a pushed `Signal` can preempt the current phase — that control-flow role, not "where it eventually lands as a percept," is why it isn't a `WorkingMemory` field despite `WorkingMemory` already holding `focused_tools`.

## Working on this repo

- **Never commit, push, or open a PR on your own initiative** — this overrides the default in agent harnesses that suggest committing and opening a draft PR at the end of an autonomous session. Implement the change, run the checks, and leave the work as uncommitted changes in the working tree for review. Commit/push/PR only when the user explicitly asks. Pushing to the public `sora-agents/sora-runtime` remote is an outward-facing, hard-to-reverse action; approval for one commit/push does not carry to the next.
- **No trailers in commit messages.** No attribution or session trailers of any kind — no `Co-Authored-By:`, no session id or URL, no "Generated with ..." line. The message ends with its last prose line. This also overrides a harness default: agent sessions are typically instructed by their own environment to append one, so it gets re-added unless it is stripped deliberately on every commit. The history records what changed and why; where a change was authored is not part of that.
- `README.md` and `EXAMPLES.md` are the living narrative spec: keep them current as part of the change that would otherwise make them stale, editing them directly rather than proposing a diff first. (The README-driven phase, where every change was specified in README.md before being implemented, is over — but "living" still means a code change that contradicts them is not finished until they are updated too.) Editing a manual in EXAMPLES.md means running `check_manuals_sync.py` before calling the work done.
- ADRs in [docs/architecture/adrs/](docs/architecture/adrs/) are append-only *once accepted*. Never edit an accepted ADR's decision in place — a changed decision gets a *new* ADR that supersedes the old one, with the old one's status line updated to `superseded by ADR-NNNN`. A `proposed` ADR *may* still be edited in place, up until it is accepted — see the lifecycle note in [docs/architecture/adrs/README.md](docs/architecture/adrs/README.md) (also the index and conventions).
- Follow TDD where practical, and prefer fakes/determinism over real network adapters or model-backed strategies until those specifically are what's being tested: real networks and real models make tests slow, flaky, and non-reproducible, so deferring them keeps the suite fast and deterministic for as long as possible.

## Four traps that have already cost real time

None of these is discoverable by reading the code.

1. **The symptom names the wrong component.** ARE's event judge checks timing *first* and reports a late-but-correct call under the same `TOOL_JUDGE_REJECT` label as a wrong-argument one; a replan defect surfaces at the step that read an empty binding, not the data-op that wrote it. Confirm which component actually failed — from the run's own trace — before changing code.
2. **A reverted experiment leaves no trace in git.** Batching a condition's queued changes (`_pursue_fired_condition` in `src/sora/_strategies/reason.py`) looks like free throughput; it dilutes the `fired_*_ids` in `SEEDED_BINDINGS` that the `then` sub-plan depends on, caused a replan storm, and was reverted off `main`. An absent optimization here may be a rejected one.
3. **A stale base disarms the guards silently.** `examples/gaia2/evaluation/campaigns/prompt/baseline.json` pins the seven semantic prompts by sha256 and `tests/test_gaia2_evaluation.py` reddens on any edit — but a worktree branched from `origin/main` while the main checkout holds uncommitted work (routine, since agents don't commit here) hashes the wrong prompts, and the tripwire goes quiet instead of red.
4. **Some breakage is silent and delayed.** A behavioral edit to `PLAN_SYSTEM_PROMPT` (`src/sora/memory.py`) invalidates comparison against every benchmark number recorded before it. The sha256 gate says a prompt moved, not that results became incomparable: a fix scoped to one call site should move exactly one row. Re-freezing to reach green without saying so is the failure.

## Architectural habits to default to

General habits, not tied to one file — the kind of thing that's easy to reintroduce by accident because it's the "natural" way to write it otherwise.

- **Protocol over inheritance** for every extension point (tools, adapters, memory backends, transport, phase strategies, actions). Don't reach for an ABC or a base class requiring inheritance.
- **New durable data goes into an existing memory module** (semantic/procedural/episodic) with a disambiguated method name — not a new memory type, no matter how narrow the new data feels.

## Code style

- Formatter/linter: `ruff` (config in `pyproject.toml`) — not manually-enforced PEP8.
- Every type is either a `@dataclass(frozen=True)` (value types) or a `Protocol` (interfaces), fully type-hinted (`mypy --strict`).
- Async-first: any method that touches I/O is `async def`.
- Docstrings only for non-obvious invariants (the *why*, not the *what*) — most types and methods have none.
- **Never cite the ROADMAP from a durable file** — not its task IDs (`A5`, `D4`, `T10`, ...), not its phase labels (`Phase 2`, `Phase 4 backlog`, ...), and not the file itself. This covers code comments, docstrings, config like `pyproject.toml`, **ADRs, design notes under `docs/architecture/`, and documentation pages under `docs/`**. The ROADMAP gets restructured — it already has once, which left dangling `ROADMAP D5`-style citations across ADR-0024 and the design notes that had to be swept out. Describe the thing itself instead: say *what* is stubbed or deferred and *why* (`# stubbed: resource_updated -> Signal wiring not built yet`; "author-declared checkpoints, deferred, are the planned generalization"), never *which* roadmap item will do it. Two narrow exceptions: the project's own front matter (`README.md`, `CONTRIBUTING.md`, `CHANGELOG.md`, this file, and `CLAUDE.md`) may link to ROADMAP.md as the status pointer, and a dated historical record that exists to capture a moment (a findings write-up named after the phase that produced it, or the frozen roadmap archive itself) may name the phase it documents.
