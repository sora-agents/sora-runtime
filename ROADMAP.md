# S-ORA Implementation Roadmap

Tracks progress from tooling setup through a working implementation of the design in [README.md](README.md) and [EXAMPLES.md](EXAMPLES.md). See [docs/architecture/adrs/](docs/architecture/adrs/) for why specific decisions were made.

Ordering principle for Phase 3: **fakes and determinism first, real networks and real models last.** Both LLM calls and real external adapters make tests slow, flaky, and non-reproducible — deferring them keeps the test suite fast and deterministic for as long as possible. Phase 2 is the deliberate exception — see its own note below.

## Phase 2 — Walking skeleton against ARE

Goal: get one full Observe→Act decision cycle running against a real external
adapter as fast as possible, to surface conceptual or design gaps in the
README/EXAMPLES.md sketch before investing in the full TDD build-out. This is
the one deliberate exception to "fakes and determinism first": ARE's MCP
server ([EXAMPLES.md](EXAMPLES.md#example-evaluating-a-s-ora-agent-on-are-meta))
runs a fixed scenario locally as a scripted, deterministic subprocess — not a
flaky live network dependency — so pulling it forward here doesn't cost the
reproducibility the TDD-first ordering is protecting. Code from this phase is
explicitly throwaway/minimal: it gets replaced and properly test-driven in
Phase 3, not polished here. Test coverage for this phase is a single
integration-level test, not unit tests per layer.

- [x] Minimal types/actions/cycle wiring needed for exactly one `tick()` — only what this spike touches, not the full API sketch
- [x] Real MCP `WorkspaceAdapter` wired to ARE's local MCP server — over **stdio** via `python -m are.simulation.apps.mcp.server.are_simulation_mcp_server --apps are.simulation.apps.email_client.EmailClientApp --transport stdio` (the sketch's `--scenario scenario_email_calendar --transport sse` form doesn't exist as written)
- [x] Hardcoded, deterministic `ReasonStrategy` that does just the *first* step — `invoke EmailClientApp.list_emails` (real tool is `EmailClientApp`, not `EmailApp`) — no LLM call, no multi-step plan yet
- [x] **Done when:** the single step completes end-to-end against the real ARE MCP server, captured as one skip-gated integration test (`tests/test_are_walking_skeleton.py`); the resulting typing corrections, documentation updates, and ADR decisions have since been incorporated.

### Track D — Decision cycle proper (mostly serial; needs A3 + the strategies)

- [x] D1. `DecisionCycle` Observe-only + `DefaultObserveStrategy`, re-driven as permanent. *(A4: promotes the spike's `observe_resolves_running_activity`, and the `NotificationQueueSink` group → `tests/test_perception.py`, its first real consumer.)* Done: `DefaultObserveStrategy` (already implemented from the spike) and `NotificationQueueSink` needed no `src/` change — this promotion pins their full contract. `tests/test_perception.py` lifts the three sink tests verbatim (incl. `drain_snapshots_current_depth`'s within-cycle no-starvation invariant) and adds the `PerceptKind` StrEnum guarantee; `tests/test_cycle.py` is the Observe home — the four channels, the automatic 1:1 running-resolution (matched/only-matched/unmatched-ack guard), and an Observe-only `tick()` that populates percepts+messages then returns without dispatching. Both promoted groups removed from `test_cycle_wiring.py` (registry + end-to-end tick groups remain until D4 retires the file).
- [x] D1a. **Observable-property percepts should be a replaced snapshot, not an append log.** `DefaultObserveStrategy.observe()` appends a fresh `PROPERTY` percept for every focused tool's property *every cycle* without clearing, so `wm.perceptions` grows unbounded and accumulates stale duplicates (surfaced while designing D3's `_filter_`). Properties are persistent, re-observed state — Observe should represent them as a replace-by-`(source, name)` snapshot (last value wins), so the current observable state is one entry per property, not a growing history. Signals are the opposite (transient, fire-and-forget) and must keep append semantics — their lifecycle is the blocked-state machinery's (Phase 4), not Observe's. D3's `_filter_` only *masks* the property growth (prunes properties from unengaged sources); this fixes it at the source. Small, self-contained Observe change with a `test_cycle.py` snapshot-vs-append test. In addition, once a tool is unfocused, corresponding properties should be removed. **Done:** `DefaultObserveStrategy` gained a `_snapshot_properties` helper that replaces a `PROPERTY` percept in place by `(source, name)` (last value wins), preserving list position; the signal/result-sink/message channels are untouched (signals still append). `UnfocusAction` now prunes the unfocused tool's `PROPERTY` percepts from `wm.perceptions` (signals from that source retained, same rationale as `_filter_`); the leave path stays covered by the next cycle's Situate `_filter_`. Homes: `tests/test_cycle.py` (snapshot-vs-append, per-name snapshot, signal-append-still-holds) and `tests/test_action.py` (unfocus removes only that tool's properties). README's `DefaultObserveStrategy`/`UnfocusAction` sketch bodies still show the old `append` form — a doc-sync diff is proposed for sign-off (README-driven rule), the prose at README's Situate section already documents the snapshot intent.
- [x] D2. `DefaultReflectStrategy` — deterministic completion/failure judgment + store-on-success to episodic (B3) and procedural (B4). Done: two asymmetric rules judge each `READY` activity — **failed** on any resolved-but-not-`ok` `last_operation` (independent of the plan), **completed** on a plan present and fully consumed (`step_index >= len(plan.steps)`); a plan-less activity is never auto-completed (protects plan-less flows). The `TERMINATED` transition is synchronous (Situate never re-selects it that cycle); episodic `learn` (both outcomes) and procedural `store` (success only) are dispatched as tracked background tasks that never block the cycle (the `InvokeAction` pattern). `cycle.py`/README unchanged (behavior already specified there); permanent tests in `tests/test_cycle.py` (unit rules + async dispatch + an integrated non-reselection tick).
- [x] D2a. Enrich the episodic experience record (builds on D2). The episode was outcome + goal only — too thin to inform later reasoning, and the failure episode is the *only* surviving copy of the attempted plan (procedural stores no failed plan). `EpisodicMemory.learn` now also records `succeeded`, the plan snapshot, step progress (`step_index`/`step_count`), and the last operation result — captured selectively from the activity `learn` already receives (not a blind `asdict(activity)`, whose freeform `context` may not serialize). Full plan inlined on both outcomes so an episode is self-contained (accepted redundancy with procedural on success). Retrieval stays exact-goal-equality; retention of fat episodes deferred. One more case the stopgap gets wrong, found by review and reproduced: because `_lift_pending_conditions` copies conditions off *every* live frame, a condition declared by the **top-level plan** holds the pop out of an entirely unrelated sub-plan — the activity goes `BLOCKED` with its frames intact and the parent's own remaining steps (the report to the user) never run. Frame-scoping is therefore part (ii)'s job and not separable from it: lifting deliberately erases which frame declared what, so the goal-kind rule needs that attribution recorded, not just a tighter predicate.

- [ ] A9. **Retirement (garbage collection) of pending conditions.** [ADR-0022](docs/architecture/adrs/0022-plan-representation-context-guard-and-subgoals.md) names the gap in its own consequences — *"an activity's watch set grows with its sub-goal depth, and nothing prunes it but `until`"* — and it is worse than that: `until` is judged only inside the **batched condition evaluation**, which only runs when an observed change makes a condition *eligible* (`_eligible_conditions`), so a condition whose watched collection goes quiet is never re-judged, never retires, and its `ConditionWait` holds the activity `BLOCKED` for good. Reachable today for a contingency condition; **load-bearing** for a maintenance sub-goal (A8), whose frame lives exactly as long as its `until`. Decided in [ADR-0027](docs/architecture/adrs/0027-achievement-and-maintenance-goals.md): **all** `until`s, not only time-bounded ones — a time-bounded `until` resolves **mechanically** against the clock (A10) at no model cost, which is the common case and the one this must not tax, while an event-shaped `until` ("the Film Production Day has taken place") still needs the judge and rides [ADR-0026](docs/architecture/adrs/0026-undeclared-relevance-recovery.md)'s **idle-scheduled** cadence, never displacing an activity that could advance. **Retire only, never fire** — a firing pass would duplicate the eligibility gate's job and reopen the cost question it settled (firing on the idle cadence would additionally recover a watch whose signal was never matched; revisit only with a measurement). **Observe retires, Reason pops** — Reason owns plan advancement everywhere else and keeps owning it here. Homes: `DefaultObserveStrategy` (the pass), `src/sora/strategies.py` (the pop).

- [ ] A10. **A domain `Clock` on the workspace.** An `until` asks about **domain** time. Every `time.time()` in the runtime today (`Percept.observed_at`, `invoked_at`, `requested_at`, an episode's `ended_at`) is *host* wall-clock and correct as infrastructure timing — the two must never merge into one "now": under a simulation the domain clock starts elsewhere *and can run at a different rate*, and `are_sim.py`'s own comment records the silent wrong-answer bug from confusing them (an agent told it was 1 Jan 1970 during a 2024-10-15 scenario). Domain time also cannot be **observed**: ARE's `SystemApp` keeps no time in `get_state()` (`get_current_time` computes from `time_manager` on call), so there is no property for poll-on-observe to publish — and if there were, a monotonically-advancing property would push `state_changed` on *every* Observe and the `_SIGNAL_RETENTION` cap would evict every real signal within one cap's worth of ticks (the motivating run took ~2400). Nor may the agent **poll** it: an invoke is an external action, and one-per-cycle ([ADR-0009](docs/architecture/adrs/0009-five-phase-decision-cycle.md)) means a maintenance goal reading a clock would starve the work it exists to do. So: a small `Clock` Protocol **per workspace** (not per agent — a simulated clock's *rate* differs, and two workspaces may legitimately disagree), defaulting to host wall-clock, which `are_sim` implements off the `Environment`'s `time_manager` (it already holds `self._env`) at no cost to the action budget. It returns an **instant**; a timezone is for rendering, never in the comparison path. An `until` resolves against the workspace owning its `watch.source`; one that would need comparing two workspaces' clocks is a plan defect. **A maintenance goal with a time-bounded `until` in a workspace with no domain clock is rejected at plan validation** — it could never terminate — feeding [ADR-0025](docs/architecture/adrs/0025-deliberation-breakers.md)'s replan path, with repeated rejection escalating to its shared terminus (await-input): the agent is missing a required capability and should say so. Homes: `src/sora/environment.py` (the Protocol), `src/sora/adapters/are_sim.py` (the ARE clock), `bootstrap.py` (wiring), `src/sora/strategies.py` (plan validation).

- [ ] A11. **Ask the user about activities blocked on long-quiet conditions.** Open question left by [ADR-0027](docs/architecture/adrs/0027-achievement-and-maintenance-goals.md): after A9, `until` is still the *only* bound on a condition, so an activity blocked on a condition that has been quiet for a very long time is indistinguishable from a healthy monitor. Candidate answer — periodically ask the user to validate such activities, reusing [ADR-0020](docs/architecture/adrs/0020-hard-interrupt-and-await-input.md)'s `InputWait` and [ADR-0025](docs/architecture/adrs/0025-deliberation-breakers.md)'s shared terminus, so no new mechanism is needed. Three constraints found while scoping it: it needs the domain clock (A10) like everything else here; the age that matters is **since the activity last did anything**, not since the condition was declared, or a healthy long-running monitor gets nagged for being healthy; and it is an *unprompted outbound message*, which in a Gaia2 run costs a turn and can be judged — so it must be **off by default** and not enabled for benchmark runs. Needs more experience before deciding; logged so the gap is not rediscovered.

- [ ] A12. **Root the derived-change path space, so `_match_derived`'s path gate actually gates.** `_derive_property_changes` calls `diff_values(previous, current)` with no root, so a derived change's path is relative to the *inside* of one property's value, while `_match_derived` never reads `PropertyChange.name` — the property that moved is dropped on the floor. A whole-property diff therefore roots at `path=""`, which `_path_matches_one` treats as matching **any** wait path, so on a tool exposing several properties a change to `contacts` satisfies a watch scoped to `events` and buys a judge call per unrelated property movement. Not fixable by simply prefixing the property name: `are_sim` computes its *announced* changes the same rootless way off a single `state` property (`diff_values(previous, state)`), so watches are authored as `events`, not `state.events` — rooting one side alone desyncs the two logs, and rooting both changes what the planner writes (`PLAN_SYSTEM_PROMPT`, hence a Gaia2 re-baseline). The real question is whether `SignalWait.path` is rooted at the property name or inside a property's value; decide that first, then make both producers agree. Reachable today only through the MCP adapter (one property per resource binding) — and its signals carry no `changes` at all, so its watches are already maximally wide, which is why this is logged rather than shipped. A second, smaller half rides along: the same-tick dedup in `_derive_property_changes` keys on `(source, change.path)`, so a signal carrying **no** `changes` (exactly what the MCP adapter pushes) contributes nothing and every announced change also gets a derived twin, and a signal reported at the root does not suppress a finer derived path (`_path_matches_one("", Change(path="events"))` is `False` — the bidirectionality runs the other way). Widening the dedup is **not** the fix on its own: it already ignores the signal *name*, so a wider suppression can drop the derived change that was the only thing matching a differently-named watch — trading a duplicate call for a missed wake, which is the trade this machinery exists to refuse. Homes: `src/sora/strategies.py` (`_derive_property_changes`, `_match_derived`), `src/sora/adapters/are_sim.py`, `src/sora/memory.py` (planner prompt).

### Track C — WoT

- [ ] C1. WoT adapter and the two-agent lab scenario (EXAMPLES.md's additional example). Includes reworking the `video-stream` device from its current placeholder — on-device scene understanding published as a text description — into a genuine raw camera feed; that toy version was a first-pass stand-in, not the intended design, and a text-only feed gives B3 (below) no real trigger.
- [ ] C2. Extend `Manual` reconciliation to WoT Thing Descriptions — the WoT half split out of the MCP-scoped reconciliation. Pair a hand-authored Markdown manual with a native WoT TD (affordances/security) for the same `Manual.id`, per the merge policy (ADR-0015). First consumer is the WoT sketch's per-Thing `MarkdownManualParser().parse(load_manual(td.id))` pairing (EXAMPLES.md); needs the WoT adapter above.
- [ ] C3. Cross-workspace tool sharing — decide whether the same tool may be a member of two workspaces. Today `_register` rejects any duplicate `Tool.id` ([ADR-0014](docs/architecture/adrs/0014-tool-identity-globally-unique.md)), so a tool cannot appear in two workspaces. That's correct for the A&A/CArtAgO *containment* view (exclusive membership, one owner) but too strict for the Web/hypermedia *index* view, where a workspace is a logical container and two workspaces — each on its own server — could legitimately reference a tool running on a third (via `Tool.address` override). ADR-0014 already put identity on a global URI, which surfaces a tension: it wants global identity *and* rejects duplicate ids as collisions. Leading candidate: split by connection ownership — connection-owned tools (`address is None`) stay exclusive; self-addressed tools (own global URI) may be referenced from multiple workspaces, with `_register` admitting a duplicate id only on canonicalized-equal address, `_workspace_tools` many-to-many, and refcounted deregistration. Couples to the `Manual` reconciliation (which manual wins for a shared tool) and the dynamic-environments refcount bookkeeping. Not needed for v0.1.0 (ARE has no shared tools); realize with the WoT adapter + two-agent lab, as an ADR refining ADR-0014. Full analysis and options in [docs/architecture/notes/cross-workspace-tool-sharing.md](docs/architecture/notes/cross-workspace-tool-sharing.md).
- [ ] C4. Multimodal model support — especially for perception (Observe). `LLMClient.complete(system, prompt) -> str` is text-only and cannot carry an image, so the README-foreseen **LLM-backed Observe** that interprets raw perception itself (*"describing a camera snapshot"*) is not yet expressible. Fix: a **richer `LLMClient` Protocol** carrying multimodal (and tool-calling) content — the same normalized-client seam as B1's two-axis decoupling. Modality is a *Protocol-shape* problem, **orthogonal** to *which model per phase* (B2's per-strategy injection): per-phase wiring picks *which* model, the richer Protocol handles *what modality* — so don't try to solve multimodal by adding more clients. Depends on B1 + B2 above. **Real trigger now:** C1's reworked `video-stream` device (raw camera feed, no on-device summarization) is what finally gives Observe a percept that actually needs vision — v0.1.0's ARE email/calendar never did, and the WoT scenario's old toy description didn't either.

### Track D — Advanced Reasoning and Planning

- [x] D1. Observe reflects percepts and signals into working memory, Situate filters them out for the selected activity, but neither percepts nor signals are currently used when inferring a plan or gorunding actions (see respective prompts in `src/sora/memory.py`). This means the agent reasons blindly, having access only to results of previous actions. Percepts should be read in memory. **Done:** `ProceduralMemory.infer`/`.ground` — and the `PlanPrompt`/`GroundPrompt` they call — now also receive the agent's currently observed properties/signals, bundled as one `PerceptSnapshot(properties, signals)` value (not two parallel `list[Percept]` params — same static type, so a call site could otherwise transpose them with nothing to catch it) extracted by `DefaultReasonStrategy` at both the planning and grounding-escalation call sites, reusing the same snapshot across both when a single `reason()` call needs it twice, rather than rebuilding it. The same narrow-extraction pattern already used for the joined-tools planning catalog (a memory module still never reaches into working memory itself). Two new reusable renderers (`render_properties`/`render_signals`, mirroring `render_tools`/`render_history`) fold into `default_plan_prompt`/`default_ground_prompt` and both system prompts, so a plan/grounding decision can read an already-observed value directly instead of reasoning blind or inventing one; both renderers JSON-render values (not `repr`, so a model told to reuse one verbatim copies a valid literal) and length-cap them like `render_history` already does. `infer`/`ground`/`default_plan_prompt`/`default_ground_prompt` keep `observed` optional (default: none observed) so untouched call sites don't break; the `PlanPrompt`/`GroundPrompt` Protocols themselves require it, so every custom prompt — not just the defaults — now sees current world state. Homes: `tests/test_procedural_memory.py` (renderers + prompt content, both `infer`/`ground` and the two `default_*_prompt` builders), `tests/test_reason.py` / `tests/test_grounding.py` (`DefaultReasonStrategy` passes the snapshot through both the planning and grounding-escalation paths). No new ADR (doesn't change percept storage/split, phase boundaries, or grounding-lives-in-Reason — only widens what the existing prompt hooks render). README's `PlanPrompt`/`GroundPrompt`/`ProceduralMemory.infer`/`.ground` sketch (plus the new `PerceptSnapshot`) has been updated to match.
- [ ] D2. Multi-field `TickResult` fusion in practice, replanning-policy experiments
- [ ] D3. Log the full execution trace as an experience — the deeper fix behind the episode enrichment (D2a). Today an `Activity` retains only `last_operation`, overwritten as each step resolves, so the per-step trace is destroyed before Reflect runs; even an enriched episode captures only the final result plus the (final) plan. Investigate retaining an append-only `(step, invocation, ack)` log on `Activity` that Reflect serializes into the episode — turning the episode into a genuine step-by-step experience. Touches the `Activity` model and Reason/Act, so larger than a memory-schema change; also revisits which step failed (currently inferred from `step_index` against the plan) and how replanning is recorded.
- [ ] D4. **Per-activity `context_adaptation` override.** The plan-reconsideration setting ([ADR-0024](docs/architecture/adrs/0024-plan-reconsideration-context-adaptation.md)) is per-agent (bootstrap `strategies.context_adaptation`); make it settable per `Activity`, so a delegated or background sub-task can commit differently from its parent — e.g. a cheap bounded sub-goal runs `none` while the foreground activity stays `before_writes`. Needs the per-agent mechanism first; couples to activity spawning/delegation (`_create_activity_`, [ADR-0022](docs/architecture/adrs/0022-plan-representation-context-guard-and-subgoals.md) sub-goals).
- [ ] D5. **Author-declared reconsideration checkpoints for dense-write tools.** `before_writes` ([ADR-0024](docs/architecture/adrs/0024-plan-reconsideration-context-adaptation.md)) assumes side-effecting ops are sparse commitment points; an embodied tool (robotic arm: move→grip→move→release per pick, plus trajectory waypoints) is nearly all writes, so `before_writes` degenerates to a judge almost every cycle. Let a tool/workflow declare coarser **checkpoints** — meaningful decision points (e.g. *before* approaching a block to grasp it) — where context is re-checked, generalizing `before_writes` (whose implicit checkpoint is "every side-effecting op"). Two carriers: an `OperationSpecification`-level flag for tools exposing composite ops (`pick(X)`), and a **sub-goal/plan-level** marker for the common case where the checkpoint is a composite boundary the primitives (`move_to`) can't express. Also a **physical-safety** boundary, not only economy: reconsidering mid-macro (gripper closed, holding a block) has already committed physically, so a checkpoint is a state where switching plans is cheap *and* safe (dovetails with the never-abandon-an-in-flight-external-op invariant, [ADR-0020](docs/architecture/adrs/0020-hard-interrupt-and-await-input.md)). Deferred: no embodied/dense-write scenario is evaluated yet.
- [ ] D6. **Purge stale reads from `Activity.history` on a reconsideration-driven replan.** `reset_for_replan()` (`src/sora/activity.py`) clears the plan, bindings, and the reconsideration baseline/verdict, but deliberately keeps `history` (the append-only `CompletedOperation` trace) and `last_operation`. That is correct for the **write** side — the new plan must know what already physically happened, so it doesn't re-send an email it already sent (the re-send hazard). It is wrong for the **read** side: reconsideration ([ADR-0024](docs/architecture/adrs/0024-plan-reconsideration-context-adaptation.md)) fires *precisely because the world moved*, so a `search_events`/`list_emails` result sitting in the prefix is the entry most likely to be stale — and a later step can `$from`-resolve its params against it, grounding the re-inferred plan on pre-change data (the mirror image of the resume re-send hazard the "replan-by-amend on resume" note in the ARE dynamic scenarios catalogue describes). `history` conflates both, so neither a blanket keep nor a blanket clear is right. The fix is now unlocked by `OperationSpecification.side_effecting` (shipped with ADR-0024): on a reconsideration/interrupt-driven replan, **retain the side-effecting acks** (keep the re-send guard) and **drop or invalidate the read results** so the new plan re-grounds against fresh perception rather than a stale prefix. Scope: `reset_for_replan` (which needs the ops' specs to classify each entry — today it takes no arguments, so this couples to how the caller reaches the registry) and the grounding read of `history`. Orthogonal to the ADR-0024 build; a distinct design decision, not a loose end from it.

## Backlog / exploratory

- [ ] X1. **ARE-over-MCP (experimental) — dynamic scenarios across a standard protocol wire.** The shape-(b) alternative split out of A2 (which shipped in-process, see the [ARE dynamic scenarios design note](docs/architecture/notes/are-dynamic-scenarios.md)): a launcher that runs `Environment.run` in a thread and serves the *live* apps via `ARESimulationMCPServer`, with S-ORA surfacing timeline changes by **poll-on-observe** (re-read `app://{app}/state` each cycle, diff, emit `state_changed`) — reusing the `are_mcp` adapter and exercising a real MCP wire. Not needed for v0.1.0; valuable as concrete protocol-interop input for the WebAgents CG. **Findings from the A2 investigation (why in-process won, what MCP would need):** (1) **Polling is not an MCP limitation** — the protocol supports asynchronous, server-initiated `notifications/resources/updated` (client `resources/subscribe`), independent of any request; S-ORA's `are_mcp` adapter already consumes exactly that path. (2) **The gap is ARE's server implementation** — it emits `resource_updated` *only* from inside the write-tool wrapper (`are_simulation_mcp_server.py`), using that request's session, and keeps no subscription registry / state watcher; a timeline-injected change happens on the `Environment` thread with no request in flight, so line-147's push mechanism is structurally unavailable. Closing it means capturing a durable client session (a FastMCP lifespan/transport hook) and pushing to it from the Environment *thread* into the server's asyncio loop — off-request **and** cross-thread. (3) **`USER_MESSAGE` has no MCP push surface at all** — the AUI is a tool + a readable `app://AgentUserInterface/state`, so a new user message is only visible by polling that resource and diffing, and it belongs on the *transport* seam, not the adapter's resource surface — so bridging it over MCP couples the adapter to the transport. Net: the MCP route needs off-request/cross-thread push plumbing that lives *in ARE*, plus a resolution for AUI→transport coupling; polling sidesteps (2) but not (3). Full rationale in the [ARE dynamic scenarios design note](docs/architecture/notes/are-dynamic-scenarios.md).
- [ ] X2. **Adaptive commitment — tune reconsideration density to the observed world-change rate.** The static `context_adaptation` setting ([ADR-0024](docs/architecture/adrs/0024-plan-reconsideration-context-adaptation.md)) approximates an unknown environmental dynamism (Kinny–Georgeff's γ): the optimal reconsideration frequency tracks how fast the world actually changes, which the agent doesn't know a priori. Explore adjusting the reconsideration density at runtime from feedback — raise it when recent judgments frequently invalidated the plan, lower it (get bolder, toward `none`) when they rarely did — so a mostly-static run converges toward cheap and a churny one toward cautious. Speculative; needs the static mechanism + multi-scenario evidence first.
